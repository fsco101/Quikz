# Deploy Quikz: Render API + Vercel frontend

Quikz runs as two services from this repository: a persistent Node.js API on Render and a static Vite frontend on Vercel. MongoDB Atlas stores accounts, academic data, avatars, and audit events. A Render persistent disk stores lesson attachments. Node.js 22 is selected in both package manifests and the Render Blueprint.

## 1. Prepare MongoDB

Create a MongoDB database and a database user with read/write access to the Quikz database. Keep its connection URI in Render's secret environment settings. Permit your Render service's outbound IP addresses in the Atlas network access list. Choose compatible regions for the service and database.

Production never falls back to temporary MongoDB if the URI is absent or unreachable. Local tests and development can still use isolated temporary databases.

## 2. Create the Render backend

After pushing the configuration to GitHub, create a **Blueprint** in Render and select this repository. Use the root `render.yaml`. It configures:

| Setting | Value |
| --- | --- |
| Root directory | `backend` |
| Runtime | Node.js 22 |
| Build | `npm ci --include=dev && npm run build && npm prune --omit=dev` |
| Start | `npm start` |
| Health check | `/api/health` |
| Service plan | Starter, with a persistent disk |
| Disk mount | `/var/data`, initially 1 GB |
| Lesson upload directory | `/var/data/quikz/uploads` |

The Blueprint selects a **paid service and disk** because Render's free service filesystem cannot preserve lesson uploads across restarts. Review the service and disk charges in Render before creating the Blueprint. For manual Web Service creation, use the same settings and attach the disk before starting the API.

Supply the prompted values:

| Variable | What to enter |
| --- | --- |
| `MONGODB_URI` | MongoDB connection URI including the Quikz database name |
| `CORS_ORIGINS` | Exact frontend origins, e.g. `https://quikz.vercel.app,https://learn.example.com` |
| `ADMIN_EMAIL` | Email for the initial administrator |
| `ADMIN_PASSWORD` | A unique strong initial administrator password, at least 6 characters and at most 72 bytes |

`JWT_SECRET` is generated by Render. Keep it stable between deploys; changing it invalidates existing sessions. The API requires at least 32 characters in production. For manual setup, generate a random secret with `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` and save it only in the hosting secret settings.

The Blueprint also sets `NODE_ENV=production`, `UPLOAD_DIR`, `SEED_DEMO_DATA=false`, and `MONGOMS_DISABLE_POSTINSTALL=1`. Render supplies `PORT`; the API binds `0.0.0.0` and uses that port. Do not copy the development `PORT=5000` into Render unless you intend to override it.

Optional `ADMIN_USERNAME` and `ADMIN_FULL_NAME` customize the initial administrator. Bootstrap creates an administrator only if none exists; it does not reset existing accounts. After verifying the administrator can log in, remove **both** `ADMIN_EMAIL` and `ADMIN_PASSWORD` from the service settings if you do not want bootstrap credentials retained. Production demo accounts are disabled by default, and the production frontend hides all demo credential buttons.

Wait for `https://<your-render-service>.onrender.com/api/health` to return HTTP 200 with `status: "ok"`. A database outage returns 503. The health response is not cached. Save the Render origin for the frontend setup.

## 3. Create the Vercel frontend

Import the same GitHub repository into Vercel as a separate project:

| Setting | Value |
| --- | --- |
| Root directory | `frontend` |
| Framework preset | Vite |
| Install command | `npm ci --include=dev` |
| Build command | `npm run build` |
| Output directory | `dist` |
| Node.js | 22.x |

`frontend/vercel.json` supplies these build settings and basic security/cache headers. Public account and catalog routes use hashes, such as `/#/login` and `/#/signup`, so no server-side SPA rewrite is required.

Before building, add this environment variable in the Vercel project:

```dotenv
VITE_API_URL=https://<your-render-service>.onrender.com
```

Use the backend **origin only**, without `/api`, another path, query parameters, or credentials. Vercel builds require HTTPS. The build fails with a clear message if this value is absent or malformed. Vite embeds it in the public JavaScript bundle; never put database credentials, JWT secrets, or administrator passwords in `VITE_*` variables. Rebuild/redeploy after changing it.

All API requests, avatars, authenticated lesson downloads, and PDF/Excel exports use this origin. They call Render directly instead of relying on the development Vite proxy. Tokens remain attached to authenticated API requests; public avatar images do not require a token.

After Vercel assigns your project domain, set Render's `CORS_ORIGINS` to that exact origin and redeploy the API if it differs from your initial value. Include custom domains explicitly. A Vercel preview using the production API must also have its exact preview origin allowed; do not allow every `*.vercel.app` origin. You can reserve the stable Vercel project hostname before the first successful frontend build.

## 4. Verify the deployed services

1. Confirm Render `/api/health` returns 200. Open the Vercel landing page and its public catalog.
2. Register a student and a faculty account, and verify each account survives a page refresh.
3. Sign in as the bootstrap administrator and check **System health**. It should report persistent MongoDB and successful write/read verification.
4. As faculty, create a subject, upload a lesson attachment, and download it. Upload an avatar and verify it renders from the Render domain.
5. Verify a PDF/Excel export after there are quiz results. The browser's requests should target Render, with the correct CORS origin returned.
6. Restart/redeploy the API, then confirm accounts, records, avatars, and the lesson attachment remain available.

The API drains HTTP requests and disconnects MongoDB on SIGTERM/SIGINT. Failed startup exits with a failing process status so the host can detect it. Health probes may omit the browser `Origin` header; browser requests from unlisted origins are rejected with 403.

## Persistence and existing data

Only files below the mounted disk path persist on Render. Back up the disk and MongoDB separately. Existing lesson records store attachment filenames; when migrating an existing installation, copy the contents of its `backend/uploads` directory into the configured `UPLOAD_DIR` without renaming the files. The API protects lesson files through `/api/modules/:id/file`; it does not expose the upload directory as public static content.

A service with a local persistent disk is intended for a single API instance. Move attachments to shared object storage before scaling to multiple instances. Increasing disk capacity and configuring backups are hosting operations; this repository does not perform them automatically.

## Local verification

```powershell
npm --prefix backend ci --include=dev
npm --prefix frontend ci --include=dev
npm --prefix backend test
npm --prefix backend run build
npm --prefix backend run test:production
npm --prefix frontend run build
npm --prefix backend audit --omit=dev
npm --prefix frontend audit --omit=dev
```

For browser coverage, run `npm run test:e2e` from `frontend`. To exercise separate frontend/API origins locally in PowerShell:

```powershell
$env:VITE_API_URL = 'http://127.0.0.1:5100'
$env:CORS_ORIGINS = 'http://127.0.0.1:3100'
npm run test:e2e
Remove-Item Env:VITE_API_URL, Env:CORS_ORIGINS
```

The production smoke check launches the compiled server with `NODE_ENV=production`, a temporary MongoDB URI and upload directory, and generated test credentials. It checks health, CORS/preflight, registration, authenticated attachments, persistence across an API process restart, and question generation from the saved attachment in that directory. It never connects to the configured application database.

The GitHub workflow runs these builds and tests on isolated infrastructure. The production runtime dependency audit is separate from development tooling; Render prunes development packages and Vercel deploys the generated static assets.
